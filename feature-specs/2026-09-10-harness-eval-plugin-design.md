## 主入口调整：从当前工作里看过程与反馈

用户在 `0001788974544787-000054-b0855f0c` 指出手动组织评测对个人日常使用成本过高；`0001788975277826-000056-ad5f2bed` 希望进一步明确 UI/UX。当前主流程调整为：正常对话/开发 → 自动记录关键过程 → 当前任务旁按需展开 → 任务完成后反馈 → 有值得追查的问题时才进入后台定向对照。下文“选择规则与任务、新建对照”的首稿流程保留为进阶调查路径，不再是默认入口。

已制作 [聊天区域交互草图](./demos/current-work-feedback/index.html)：安静的一行过程入口；右侧查看或消息内展开；关键步骤/本次输入/反馈三层；来源暂不可读、无记录与完成场景。用户可以在同一预设任务上比较布局。它是独立组件实验、演示数据，未挂载到生产聊天组件，也没有真实采集或自动评分。

默认推荐侧边查看：聊天正文与输入保持原位；窄屏用可返回的详情层。原始输入按当时版本、渠道和可见性展开；过程事实、任务完成判断和 skill 净收益分开，不用调用次数直接给价值分数。较长的持续阅读/对照仍可沿既有工作区能力扩展，侧栏不是所有对象的永久宿主。

## 一句话产品

**选择一条规则和一个模型，让工具做可追溯的任务对照，直接看这条规则在哪些任务上值得保留、需要调整，或还不能下结论。**

现在：用户催推进、猫找临时目录、拼版本与日志、解释不同测试数、用户再追问结论。

目标：版本与任务已关联 → 一次确定对照范围和预算 → 自动执行与核验 → 页面说明改变了什么判断 → 用户只处理机器不能决定的价值取舍或授权。

它评估具体规则在具体任务上的作用。质量、时间、费用与用户干预分开显示；不把不同单位混成“猫猫总分”。本地优化中的确定性脚本错误仍由测试/代码修复，不强行变成模型评测题。

## 用户如何使用

| 用户所在页面 | 用户看到什么、能做什么 | 工具承担的工作 |
|---|---|---|
| 设置 → 插件卡片 | 安装版本、可用模型、授权状态、当前是否真在运行；完成必要设置 | 校验发布包、展示具体缺口；安装不自动启动模型任务 |
| 评测工作台 → 规则列表 | 选择 Prompt 段、skill 或规则组合；每项显示版本、任务类别、已有结论及证据范围 | 读取获准来源并固定版本；“目录存在”“已挂载”“本次确实读取”分别显示 |
| 新建对照 | 选择模型、任务集与“现行版/候选版”；预览实际差异、预算、环境和验证方法 | 自动补可读配置；只询问无法推断的目标、价值取舍和执行授权 |
| 运行页 | 正在执行哪项、已完成/失败/待恢复；可停止；离开页面后还能回来 | 有界执行、日志与结果持久化、中断恢复、失败归类与去重 |
| 结果页 | 一句结论 + 适用范围 + 质量/成本变化 + 前后具体行为；点开原始证据 | 按已冻结方法汇总，不挑最好一次；报告无法归因、样本不足与环境干扰 |
| 采用建议 | “保留当前版”“准备调整”“继续观察”；旁边有支持和反对证据 | 生成建议和变更草稿；实际写回仍交给资产 owner 的授权流程 |

首版必须支持完整的“选规则 → 配对照 → 执行/恢复 → 看证据 → 得到建议”旅程。导入已有回放是同一结果模型的入口，可加速设计验证，但单独做一个导入仪表盘不算完整工具。

## 插件化方式

采用**可独立开源的评测核心与结果视图 + Clowder AI 适配层**。逻辑接口在下表定义，尚非已发布 API 或 manifest capability。

```mermaid
flowchart LR
  U[用户在评测工作台选择规则与任务] --> H[宿主适配层：身份、权限、受管执行]
  H --> C[开源评测核心：冻结对照、核验可比性、汇总结果]
  C --> R[结果视图：具体收益、代价、证据与不足]
  H --> A[模型与任务执行器]
  A --> S[原始来源与任务产物]
  S --> C
  R --> O[规则 owner 的变更流程]
```

| 部分 | 拥有什么 | 不拥有什么 |
|---|---|---|
| 开源核心 | ExperimentSpec、RunEvidence、ComparisonResult 等可移植数据格式；可比性与汇总算法；规则/任务适配接口 | Clowder 用户、猫、thread、生产数据、凭据与全局工作流状态 |
| 可移植结果视图 | 读取同一结果格式，展示对照、限制和证据引用；可作为独立报告查看器 | 不凭页面状态启动进程、修改规则或授予权限 |
| Clowder 插件适配层 | 来源坐标转换、core 的输入输出适配、已声明能力的使用 | 不复制原始对话/画像作为自己的数据库，不决定 Host 路由和授权 |
| Clowder 宿主与既有领域 owner | 安装/授权/进程、任务状态、数据持久化、原始轨迹、评测结论生命周期与写回审批 | 不把公开核心硬编码到本项目的 F 号或 catId |
| 独立运行宿主 | 社区使用时提供自己的来源、模型连接、隔离执行、授权与持久化实现 | 不要求接入 Clowder 才能读取结果或实现适配器 |

在 Clowder 中复用既有 owner：请求与轨迹引用来自 F299/F153；F192 持评测登记/触发/verdict，F267 持有效性与证据角色/曝光/holdout 引用，F266 持复评/关闭，F246 持审批，F313 承接交付与 outcome 闭环；需要长期改进编排时由 F311 连接，不新建另一套 Program/审批/复评账本。独立使用时由外部宿主实现同一逻辑端口，结果格式不含强制 F-number。

## 一次对照需要保存什么

| 对象 | 必要内容 |
|---|---|
| 规则版本 | Prompt/skill 正文 hash、引用版本、作用位置；单规则或组合变更明确标注 |
| 模型与执行环境 | 请求模型标识、provider 实际回报版本（缺失即未知）、CLI/runtime、参数、工具/权限、依赖、缓存与隔离环境 |
| 任务规格 | 原始任务、起始状态、任务集版本、结果检查方式、成功标准、预算与允许副作用 |
| 对照计划 | A/B 或 baseline/移除/改写，多次运行与顺序策略；预先约定停止条件、排除规则和最小有意义差异；任务集的证据角色（发现/选解/归因/独立验收）与 optimizer/rubric-selection exposure 引用 |
| 执行证据 | run/attempt ID、真实开始结束、输入投递证据、实际工具行为、源码/产物 hash、退出原因与所有失败 |
| 判定 | 独立结果检查、judge/rubric 版本与可见材料、结果可比性、质量与成本分量、限制和建议 |

只读公开设计稿不触发模型执行；实际 run 必须在宿主授权后进入隔离任务环境。对照两臂都从相同快照开始，不能让 B 继承 A 的代码、修复结果或缓存状态而不记录。输出判断标准与 holdout 的标准答案不进入被测者上下文。

已用于发现问题、选择候选、调整 Prompt 或选择 rubric 的任务集，记录其 exposure 与使用轮次；同集复测只支持该集上的局部观察。独立验收使用候选与 rubric 冻结后才揭示的封存任务，或之后自然产生的新任务，并保留来源与隔离证明。被测者执行任务当然会看到必要输入，但候选优化者不能提前利用验收答案或结果反复选解。缺少角色/曝光/隔离证明时，不把结果当作独立验收或泛化收益；相关主张标为证据不足。

缺少某条规则实际被读取的证据时，界面可以报告任务结果，却不能把差异归因给它。批量一起修改 skill 和检查脚本时，归因单位是整组干预，不拆分捏造各条收益。环境错误、超时、取消、无效样本均可见；不得只汇总成功运行。

## 如何形成结论

先检查任务质量与关键边界，再看成本；代价取舍来自所选任务的标准，不预设一个全场景权重。

| 展示项 / claim | 判定来源与分母 | 失效条件 / 动作 |
|---|---|---|
| 任务质量是否达标 | 任务 owner 定义的可复核验收；按独立 episode/输入机会计算，不按 test 函数数量 | 验收未覆盖目标、快照不匹配或结果不可读 → 不得质量放行 |
| 目标摩擦是否减少 | 可追溯轨迹中的预定义机会与行为，例如已有证据时是否重复生成等价演示 | 轨迹不完整或必要性存在争议 → 未知/交独立复核，不按 shell 次数直接判浪费 |
| 时间与资源变化 | 同任务可比较配对；完整分布、分位数或配对差值与不确定性；保留失败与环境状态 | 模型/环境差异、缓存不受控、样本不足 → 降低主张或证据不足 |
| 是否更省用户心力 | 实际用户介入及返工，区分自主判断、必要授权与系统故障；必要时由价值 owner 判断 | approval=never 的实验不能证明减少人工确认；未覆盖真实人机旅程不能自动下价值结论 |

四角色：observer 为受限采集/验收适配器；domain owner 为任务与规则负责人；consumer 为决定保留/调整的规则 owner/co-creator；calibrator 为未参与候选优化的独立复核者。若兼任必须说明，开放价值主张不能由作者独自校准。

输出“有帮助 / 有条件帮助 / 无实质增益 / 有副作用 / 证据不足”，均带任务范围和证据强度。“没有观察到差异”不是“证明无实质增益”：后者需要预定义等效区间及足够精度。一次试跑只能提供观察，不能靠默认最少几次就获得统计结论。

首版优先采用确定性结果检查。加入 LLM judge 时需另外冻结 rubric、盲化顺序、独立校准样本与人工成本预算；校准超出预设失效阈值时，停用其自动建议权并显示结果待复核。预算用尽即停，不让工具为了显著性无上限重跑。定期自动评测是后续明确选择的模式：选择后才补事件/时间触发、最大沉默时间、去重与成熟/可行动条件。

## 中断、权限与数据

任务状态建议为 draft → ready → queued → running → verifying → completed；blocked、interrupted、failed、cancelled 是独立事实。completed 表示执行与报告完成，不表示规则有益。

- 身份/配置、用户启用意图、插件健康与实验状态分别呈现；服务重启后先对账，不能继续显示假 running。
- 同一实验重试产生新的 attempt，保留失败；重放事件以稳定 ID 去重。支持断点的步骤从已核对结果继续，不支持的明确重试，不悄悄覆盖或重复计分。
- 只接受 catalog 校验过的执行器；插件安装不等于允许读取全部历史或外发。授权失效显示“重新连接/改用可用模型”，不要求抄 token 或裸命令。
- 用户可见实验、结果与处置默认持久化。禁用停止新任务，升级保持旧结果可读，卸载撤销授权但保留可导出的用户记录；删除需要用户明确选择。
- 原始对话、画像与秘密留在其 owner。公开分享前生成可审阅的脱敏导出包，不自动把本次社区样例、仓库内容或日志上传。

## 开源范围与实现顺序

可以开放：版本化数据格式、对照/可比性算法、结果视图、adapter 接口、无私有数据的合成 fixture、打包与兼容测试。保留在宿主：账号凭据、身份与路由、治理授权、实际原始数据与对应存储。

实现按永久产品能力组织，避免做完一次演示再重写：

1. 固定公共结果/任务/规则版本模型，同时定义 Clowder 与独立宿主各自的来源、执行和持久化端口；核准真实契约缺口。
2. 打通冻结任务的受管对照执行、恢复与独立结果检查，同时接入可移植结果视图；已有真实回放用作带限制的导入案例，合成输入用作可公开测试。
3. 完成 Settings 安装/授权到工作台结果/建议的整条旅程，再验证发布包在空白 consumer 中运行、升级/卸载保留数据和导出边界。

设计进入实现前需冻结：首发宿主接入方式、允许的任务副作用、默认预算及哪些结果允许自动生成建议。这些尚未获得运行授权；本轮只设计，不安装、不运行新评测、不发布。

产品完成必须有真实旅程证据：用户不再手工搬日志、对版本或催下一步，结果可复核，失败可恢复。CI 全绿、插件能安装或页面好看均不能单独宣布该目标完成。
